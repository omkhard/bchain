▶ What is a Reentrancy Attack?

A reentrancy attack happens when an external contract call is made before updating internal state. The called contract can recursively call back into the vulnerable function.

// ❌ VULNERABLE PATTERN
function withdraw(uint amount) public {
    require(balances[msg.sender] >= amount);
    // External call BEFORE state update
    (bool ok,) = msg.sender.call{value: amount}("");
    balances[msg.sender] -= amount; // Too late!
}
💡 The 2016 DAO hack drained ~$60M ETH using exactly this pattern.
▶ The Fix: Checks-Effects-Interactions (CEI)

Always follow this order: 1) Check conditions, 2) Effect (update state), 3) Interact (external call).

// ✅ SAFE — CEI Pattern
function withdraw(uint amount) external nonReentrant {
    require(balances[msg.sender] >= amount); // Check
    balances[msg.sender] -= amount;          // Effect
    (bool ok,) = msg.sender.call{value: amount}(""); // Interact
    require(ok);
}
▶ ReentrancyGuard Mutex

OpenZeppelin's ReentrancyGuard sets a lock before execution and releases it after, blocking any recursive calls.

// Simplified ReentrancyGuard logic:
modifier nonReentrant() {
    require(_status != ENTERED); // Is locked?
    _status = ENTERED;           // Lock
    _;                           // Run function
    _status = NOT_ENTERED;       // Unlock
}
▶ External Call in Loop

Calling external contracts inside a loop is dangerous: each iteration can re-enter, and a single failure reverts the whole loop.

// ❌ DANGEROUS
for (uint i = 0; i < users.length; i++) {
    users[i].call{value: reward}(""); // Any user can re-enter!
}
💡 Use Pull Payment: let users withdraw themselves instead of pushing to all.
