▶ What is a Reentrancy Attack?
A reentrancy attack occurs when an external contract call is made before updating internal state. The called contract can recursively call back into the vulnerable function, draining funds or corrupting state.
// VULNERABLE PATTERN function withdraw(uint amount) public { require(balances[msg.sender] >= amount); // ❌ External call BEFORE state update (bool ok,) = msg.sender.call{value: amount}(""); balances[msg.sender] -= amount; // Too late! }
💡 Famous example: The 2016 DAO hack drained ~$60M ETH using this exact pattern.
▶ Checks-Effects-Interactions (CEI)
The safest pattern to prevent reentrancy. Always follow this order: 1) Check conditions, 2) Update state (effects), 3) Make external calls (interactions).
// SAFE PATTERN — CEI Applied function withdraw(uint amount) public { // ✅ Check require(balances[msg.sender] >= amount); // ✅ Effect — update state FIRST balances[msg.sender] -= amount; // ✅ Interact — call AFTER state update (bool ok,) = msg.sender.call{value: amount}(""); require(ok); }
▶ ReentrancyGuard (Mutex Lock)
OpenZeppelin's ReentrancyGuard provides a mutex that prevents a function from being called recursively. Use the nonReentrant modifier.
// Using OpenZeppelin ReentrancyGuard import "@openzeppelin/contracts/security/ReentrancyGuard.sol"; contract Safe is ReentrancyGuard { function withdraw(uint amount) public nonReentrant { require(balances[msg.sender] >= amount); balances[msg.sender] -= amount; (bool ok,) = msg.sender.call{value: amount}(""); require(ok); } }
💡 The nonReentrant modifier sets a lock before execution and releases it after, blocking recursive calls.
▶ Cross-Function Reentrancy
More subtle: an attacker calls function A which makes an external call, then re-enters via a different function B that shares the same state variable.
// VULNERABLE — Cross-function attack possible mapping(address => uint) public balances; function withdraw() public { uint bal = balances[msg.sender]; (bool ok,) = msg.sender.call{value: bal}(""); // ← re-enter via transfer? balances[msg.sender] = 0; } function transfer(address to, uint amt) public { require(balances[msg.sender] >= amt); // ← can be exploited mid-withdraw balances[msg.sender] -= amt; balances[to] += amt; }
▶ Read-Only Reentrancy
A newer attack vector where a re-entrant call reads stale state from a contract mid-execution. Even if no funds are drained directly, incorrect prices or balances can be used for flash loan attacks.
💡 Commonly affects DEX integrations and oracle reads. Curve Finance was exploited via this vector in 2023.
